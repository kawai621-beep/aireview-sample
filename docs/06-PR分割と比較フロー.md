# 06. PR分割と比較フロー

本ドキュメントでは、CodeRabbit と cubic.dev に**同一の入力（PR差分）**を与えて公平に比較するための、ブランチ構成とレビュー実施手順を定義する。

> 埋め込む問題のID（A1〜D4）と難易度の定義は [`05-埋め込んだ問題一覧.md`](./05-埋め込んだ問題一覧.md) を参照。本ドキュメントでは問題の詳細を重複記載しない。

---

## 1. 設計の基本方針

両ツールとも「Pull Request の差分」を入力としてレビューする。したがって:

- **main ブランチには問題を一切混入させない**（健康な骨組みのみを置く）。
- 問題は **feature ブランチ側にのみ** 実装する。
- これにより、両ツールが見る差分が完全に一致し、入力の差による不公平を排除できる。

---

## 2. main ブランチの構成（ベースライン）

main には以下の「健康な骨組み」のみを置く。これ自体にセキュリティ問題やN+1等は含めない。

| カテゴリ | 内容 |
|---|---|
| ドキュメント | `docs/` 配下の全仕様書（00〜07）と `docs/08-結果/` の空ディレクトリ |
| プロジェクト設定 | `package.json`（npm workspaces）、`tsconfig.base.json`、`.eslintrc.cjs`、`.prettierrc`、`.gitignore` |
| 共通型 | `shared/types.ts` |
| バックエンド骨組み | `server/`（Expressアプリ、`/health` エンドポイントのみ実装、Prismaクライアント初期化） |
| フロント骨組み | `client/`（React + Vite、ルータとレイアウトのみ） |
| スキーマ | `server/prisma/schema.prisma`（**クリーンな**モデル定義。インデックス欠如等の問題は feature 側で仕込む） |

---

## 3. feature ブランチと PR の分割（4本）

各 feature ブランチは **すべて main から派生** させる。直列にマージしないことで、各PRの差分が重複せず、独立して評価できる（マージ順序の影響を避ける）。

各PRのサイズ目安は **200〜500行**。AIレビューツールは差分が1000行を超えるあたりから精度が落ちる傾向があるため、実運用のPRサイズに近づける。

| PR | ブランチ | 主な問題カテゴリ | 含む問題ID |
|---|---|---|---|
| PR-1 | `feature/backend-auth` | 認証・認可・入力バリデーション | A1, A2, A3, A4, A5, A6, A7, A8, C2 |
| PR-2 | `feature/backend-posts` | N+1・SQLインジェクション・IDOR・可読性 | B1, B2, B3, B4, B5, B6, B7, B8 |
| PR-3 | `feature/backend-ops` | 並行性・タイムゾーン・リソースリーク・情報漏洩 | C1, C3, C4, C5, C6, C7 |
| PR-4 | `feature/frontend` | XSS・秘密情報埋め込み・型安全性・重複 | D1, D2, D3, D4 |

> ※ C2（会員登録の競合）は `register` メソッドに由来するため、認証機能を実装する PR-1 で評価する。

各問題IDの詳細（対象ファイル、問題の形、難易度、本来あるべき修正）は [`05-埋め込んだ問題一覧.md`](./05-埋め込んだ問題一覧.md) を参照。

### 分割の狙い

- **1PR巨大化の回避**: 差分が大きすぎるとツールが「差分長すぎ」で精度低下する。
- **カテゴリ別スコアリング**: 「セキュリティはどちらが強いか」「可読性指摘はどちらが深いか」など、カテゴリ毎の比較が可能になる。
- **独立評価**: 各PRを独立して両ツールにレビューさせ、結果を `docs/08-結果/{ツール}/{PR番号}.md` に格納する。

---

## 4. PR作成手順

各 feature ブランチについて以下の手順でPRを作成する（リモートリポジトリは GitHub を想定）。

```bash
# main を最新化
git switch main
git pull origin main

# feature ブランチを作成（main から派生）
git switch -c feature/backend-auth

# ... 問題を含む実装を行う ...

# 型チェック・ビルド確認
npx tsc --noEmit
npm run build -w client

# コミット
git add -A
git commit -m "feat(backend): 認証・認可機能を実装"

# プッシュしてPR作成
git push -u origin feature/backend-auth
gh pr create --title "feat(backend): 認証・認可機能" --body "..." --base main
```

> PR本文（description）には問題のヒントを書かないこと。ツールが本文に引っ張られないよう、中立な機能説明にとどめる。

---

## 5. レビューツールの設定手順

両ツールをリポジトリに連携する。一度設定すれば全PRで自動レビューされる。

### CodeRabbit
1. https://coderabbit.ai にサインイン（GitHubアカウント連携）。
2. 対象リポジトリを CodeRabbit にインストール/接続。
3. 必要に応じて `.coderabbit.yaml` でレビュー設定（言語=TypeScript、レビュー深度など）を調整。
4. PRがOpenになると自動的にレビューが開始される。

### cubic.dev
1. https://cubic.dev にサインインし、リポジトリを接続。
2. GitHub App または OAuth でインストール。
3. PRがOpenになると自動的にレビューが開始される。
4. （CLI/MCP経由でのローカルレビューも可能だが、公平比較のため本番はPRベースの自動レビューを使用する。）

---

## 6. レビュー実施手順

1. main にベースライン（健康な骨組み + docs）をマージしておく。
2. 各 feature ブランチで問題を含む実装を行い、PRを作成（Draft ではなく Open）。
3. PRがOpenになると、CodeRabbit と cubic.dev が **同一の差分** に対して自動レビューを開始する。
4. 両ツールのレビュー完了後、それぞれの指摘コメントを以下にエクスポートする:
   - `docs/08-結果/coderabbit/PR-{N}-{名称}.md`
   - `docs/08-結果/cubic/PR-{N}-{名称}.md`
5. [`07-採点方法.md`](./07-採点方法.md) に沿って、問題IDごとに両ツールの検出スコアを採点する。
6. 全PRの採点が完了したら `docs/08-結果/summary.md` で総合比較表をまとめる。

---

## 7. 公平性を保つための注意事項

- **両ツールに同じ差分を見せる**: feature ブランチは main から独立派生させ、他のPRを取り込まない。
- **PR本文は中立に**: 問題のヒントを書かない。
- **同タイミングでレビュー**: コード修正後に再レビューさせない（初期差分に対する一回きりのレビューで比較する）。
- **設定を統一**: 両ツールのレビュー深度/対象言語の設定は可能な限り同等にする。
