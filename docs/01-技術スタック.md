## 2. 選定理由

技術選定の最優先基準は **「AIレビューツールが学習データとしてよく目にする、典型的で普及した構成であること」** です。マイナーな技術や過剰にモダンな構成だと、ツールの学習データが少なく、純粋な「問題検出力」の比較ができなくなります。

### 2.1 Express + Prisma + SQLite（バックエンド）

- Express は Node.js Web FW で **最も普及** しており、レビューツールが学習しているパターンが豊富。
- Prisma はモダン TypeScript ORM のデファクト。N+1 問題を自然に書けるほか、生 SQL クエリ（`$queryRawUnsafe`）も書けるため SQL インジェクションのデモも可能。
- SQLite は **セットアップ不要・CI 不要**（ファイル1つ）で、PostgreSQL のような外部依存を避けられる。Prisma で透過的に扱える。
- NestJS 等の重い FW はボイラープレートが多く、問題が埋もれてしまうため不採用。

### 2.2 React + Vite（フロント）

- React は SPA FW で最も普及。`dangerouslySetInnerHTML` などの API を通じて XSS を自然に埋め込める。
- Vite はモダンなフロントビルドツールの標準。設定が最小で、型チェック・ビルド検証が容易。
- Next.js の SSR/RSC は今回のスコープではノイズになるため外し、純粋な SPA とする。

### 2.3 npm workspaces（モノレポ）

- `server/`・`client/`・`shared/` の3ワークスペースで管理。`shared/` でフロント・バック間の共通型を共有する。
- yarn/pnpm ではなく npm にしたのは、追加インストールなしで動く標準ツールだから。

### 2.4 ESLint / Prettier を「設定のみ」配置する意図

- 意図的に緩いルール（例: `@typescript-eslint/no-explicit-any: "off"`）にしておくことで、**「Lint 設定の不備」自体をレビュー指摘の対象** に含められる。
- ただし `npm run lint` を通すことは要件としない（問題コードを残すため）。

### 2.5 テストを書かない意図

- **「テスト不足」自体をレビュー指摘項目の1つ** として扱うため、あえてテストを配置しない。

## 3. セットアップ手順

```bash
# 1. 依存パッケージのインストール（workspaces 全体）
npm install

# 2. Prisma クライアントの生成
npx prisma generate

# 3. 開発サーバの起動
npm run dev
```

### 3.1 開発時のコマンド（ルート package.json の scripts 想定）

| コマンド | 内容 |
|---|---|
| `npm run dev` | server と client を開発モードで起動 |
| `npm run build` | 全ワークスペースをビルド |
| `npm run typecheck` | 全ワークスペースで `tsc --noEmit` を実行 |
| `npm -w server run dev` | server のみ起動 |
| `npm -w client run dev` | client（Vite）のみ起動 |

### 3.2 動作確認

- サーバ起動後 `GET http://localhost:3000/health` が `200` を返せば、バックエンドの最低限のセットアップは完了です。
- クライアントは Vite の開発サーバ（既定 `http://localhost:5173`）で画面が表示されれば完了です。

> **注意**: 本アプリは意図的に問題を含むため、`npm run lint` や `npm test` は通ることを想定していません。詳細は [00-目的と方針](./00-目的と方針.md) を参照してください。
