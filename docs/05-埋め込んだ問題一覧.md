# 埋め込んだ問題一覧

> この文書は、AIレビュー性能比較のためにリポジトリに**意図的に埋め込んだ問題**の正解表（オラクル）です。CodeRabbit / cubic.dev がそれぞれの問題を検出できるかを採点する際の基準となります。
>
> 本リポジトリは本番運用を想定していません。ここに挙げたコードは**すべて脆弱性・アンチパターンを含む**ため、他プロジェクトに流用しないでください。

---

## 1. この文書の使い方

- 各問題には **ID**（A1, B3, C2 …）、**カテゴリ**、**難易度**、**問題の形**、**本来あるべき修正**、**期待される検出挙動** を記載します。
- レビュー実施後、各ツールの指摘をこの表と照合し、`docs/07-採点方法.md` のルーブリックに沿って採点します。
- 問題は **PR 単位**で分割して実装されています（`docs/06-PR分割と比較フロー.md` 参照）。

---

## 2. 難易度の定義

| 難易度 | 定義 | 期待される挙動 |
|---|---|---|
| **低** | パターンマッチで検出可能な定番問題。 | 両ツールとも**確実に検出**すべき（◎）。取りこぼしは重大な減点対象。 |
| **中** | 文脈を読まないと判定できない問題。実装の意図や複数行にまたがる。 | **優秀なツールなら検出**（○）。精度の差が出やすい層。 |
| **高** | 深い推論やセキュリティ知識・並行性の理解が必要な問題。 | **深い分析力があるツールのみ検出**（△）。識別力を分ける層。 |

集計時は難易度ごとに Recall を算出します（`docs/07-採点方法.md`）。特に「高難易度での Recall 差」が両ツールの能力差を反映します。

## 4. 問題詳細

### PR-1: `feature/backend-auth`（認証・認可・入力）

#### A1: パスワードの弱ハッシュ化（base64エンコード）
- **ファイル**: `server/src/auth/password.ts` (`hashPassword`)
- **カテゴリ**: セキュリティ / 認証
- **難易度**: 低（◎）
- **問題の形**: `Buffer.from(password).toString('base64')` のように、パスワードをエンコードするだけ（あるいは自前の簡易ハッシュ）。base64は復号可能であり「ハッシュ」ではない。
- **本来あるべき修正**: bcrypt / argon2 / scrypt などの適切なアルゴリズムとソルトを使用（cost ≥ 12）。
- **期待される検出挙動**: 両ツールとも「パスワードをbase64でエンコードしている」「平文同然・復号可能」と指摘すべき。

#### A2: パスワード比較のタイミング攻撃
- **ファイル**: `server/src/auth/password.ts` (`verifyPassword`)
- **カテゴリ**: セキュリティ / 認証
- **難易度**: 高（△）
- **問題の形**: ハッシュ値またはパスワードの照合を `===` で行い、文字列比較の早期終了タイミングを観測可能にしている。
- **本来あるべき修正**: `crypto.timingSafeEqual` の使用、または bcrypt/argon2 の `compare` 関数に任せる（ライブラリは定数時間比較を実装済み）。
- **期待される検出挙動**: タイミング攻撃の可能性に言及できるかが鍵。深いセキュリティ理解があるツールのみ指摘。

#### A3: JWT の `alg: none` 許可
- **ファイル**: `server/src/auth/jwt.ts` (`verifyToken`)
- **カテゴリ**: セキュリティ / 認証
- **難易度**: 高（△）
- **問題の形**: `jwt.verify(token, secret, { algorithms: ['none', 'HS256'] })` のように `'none'` アルゴリズムを許可。攻撃者は署名なしトークンで認証を通過できる。
- **本来あるべき修正**: `algorithms: ['HS256']`（または使用する単一アルゴリズム）に固定し、`'none'` を絶対に許可しない。
- **期待される検出挙動**: `alg: none` 脆弱性（CVE-2015-9235 系）を認識できるかが鍵。

#### A4: 秘密鍵・トークンのハードコード
- **ファイル**: `server/src/config.ts`
- **カテゴリ**: セキュリティ / 設定
- **難易度**: 低（◎）
- **問題の形**: `JWT_SECRET = "super-secret"`、`ADMIN_TOKEN = "admin123"` のように機密値をソースコードに直接記述。
- **本来あるべき修正**: 環境変数（`process.env.JWT_SECRET`）から読み込み、起動時に必須チェックを行う。`.env` は `.gitignore` で管理。
- **期待される検出挙動**: 両ツールともハードコードされた秘密を指摘すべき。

#### A5: CORS の過剰な許可（origin \* + credentials）
- **ファイル**: `server/src/app.ts`
- **カテゴリ**: セキュリティ / 設定
- **難易度**: 低（◎）
- **問題の形**: `cors({ origin: '*', credentials: true })`。ワイルドカードオリジンと資格情報送付の同時許可はブラウザ仕様でも弾かれるが、設定自体が危険。
- **本来あるべき修正**: `origin` を許可リスト（特定ホスト）に限定。`credentials: true` と併用する場合は必ず固定オリジン。
- **期待される検出挙動**: CORS 設定の危険な組み合わせとして指摘すべき。

#### A6: 管理者APIの認可欠如（IDORの一種）
- **ファイル**: `server/src/routes/admin.routes.ts`
- **カテゴリ**: セキュリティ / 認可
- **難易度**: 中（○）
- **問題の形**: 管理者専用ルータにロールチェックミドルウェア（`requireRole('ADMIN')` 等）を装着せず、ログイン済みなら誰でも `/api/admin/users` にアクセス可能。
- **本来あるべき修正**: 管理者ルータの先頭に認可ミドルウェアを適用し、`role === 'ADMIN'` を検証。
- **期待される検出挙動**: ルータ定義とミドルウェア装着の有無を突き合わせて指摘できるか。

#### A7: ログインのレートリミット欠如
- **ファイル**: `server/src/routes/auth.routes.ts` (`login`)
- **カテゴリ**: セキュリティ / 耐障害性
- **難易度**: 中（○）
- **問題の形**: ログインエンドポイントに試行回数制限がなく、ブルートフォース攻撃が可能。
- **本来あるべき修正**: `express-rate-limit` 等でIP/アカウント単位の制限を導入。アカウントロックや指数バックオフも検討。
- **期待される検出挙動**: 「レートリミットがないためブルートフォース可能」と指摘できるか。

#### A8: 入力バリデーション欠如（会員登録）
- **ファイル**: `server/src/routes/auth.routes.ts` (`register`)
- **カテゴリ**: 堅牢性 / 入力検証
- **難易度**: 低（◎）
- **問題の形**: email 形式・パスワード長・ユーザ名文字種を検証せず、`req.body` をそのまま使用。
- **本来あるべき修正**: zod / yup / express-validator 等でスキーマバリデーションを実施。
- **期待される検出挙動**: 両ツールともバリデーション不在を指摘すべき。

### PR-2: `feature/backend-posts`（N+1・SQLi・IDOR・可読性）

#### B1: 投稿一覧のN+1（著者を個別取得）
- **ファイル**: `server/src/routes/posts.routes.ts` (`listPosts`)
- **カテゴリ**: パフォーマンス / DBアクセス
- **難易度**: 低（◎）
- **問題の形**: 全投稿を取得した後、`for` ループ内で各投稿の `authorId` ごとに `prisma.user.findUnique()` を個別に呼び出す。投稿N件で N+1 クエリ。
- **本来あるべき修正**: `prisma.post.findMany({ include: { author: { select: { id, name } } } })` で結合取得。
- **期待される検出挙動**: ループ内のDBアクセスとして両ツールとも指摘すべき。

#### B2: 投稿詳細の二重N+1（コメントの著者を個別取得）
- **ファイル**: `server/src/routes/posts.routes.ts` (`getPost`)
- **カテゴリ**: パフォーマンス / DBアクセス
- **難易度**: 中（○）
- **問題の形**: 投稿＋コメントを取得した後、コメントごとに `getUser(comment.authorId)` を呼び出す。ネストが深く一見では分かりにくい。
- **本来あるべき修正**: `include: { comments: { include: { author: true } } }` で一括取得。
- **期待される検出挙動**: ネストしたループ内の個別取得を見抜けるか。

#### B3: フィードの「モダン装飾N+1」（Promise.all）
- **ファイル**: `server/src/routes/posts.routes.ts` (`getFeed`)
- **カテゴリ**: パフォーマンス / DBアクセス
- **難易度**: 高（△）
- **問題の形**: `Promise.all(postIds.map(id => getComments(id)))` のように `Promise.all` で並行化しているため一見モダンに見えるが、依然としてIDごとにクエリを発行しておりN+1。
- **本来あるべき修正**: `prisma.post.findMany({ where: { id: { in: postIds } }, include: { comments: true } })` で一括取得。
- **期待される検出挙動**: `Promise.all` の見せかけの最適化を見抜けるかが鍵。

#### B4: 検索のSQLインジェクション（`$queryRawUnsafe`）
- **ファイル**: `server/src/services/search.service.ts` (`searchPosts`)
- **カテゴリ**: セキュリティ / インジェクション
- **難易度**: 低（◎）
- **問題の形**: `prisma.$queryRawUnsafe(\`SELECT ... WHERE title LIKE '%${q}%'\`)` のようにユーザ入力を文字列補間でSQLに埋め込む。
- **本来あるべき修正**: パラメータ化（`$queryRaw\`...WHERE title LIKE ${pattern}\``）、または Prisma の `where: { title: { contains: q } }` を使用。
- **期待される検出挙動**: `$queryRawUnsafe` ＋補間として両ツールとも指摘すべき。

#### B5: ソート順のSQLインジェクション（ORDER BY 文字列結合）
- **ファイル**: `server/src/routes/posts.routes.ts` (`listPosts`)
- **カテゴリ**: セキュリティ / インジェクション
- **難易度**: 中（○）
- **問題の形**: `ORDER BY ${sortBy} ${order}` のように、ソートカラム・方向をユーザ入力から直接文字列結合。
- **本来あるべき修正**: `sortBy` / `order` を allowlist（`['createdAt','title']` × `['asc','desc']`）で検証し、不正値はデフォルトにフォールバック。
- **期待される検出挙動**: ORDER BY への注入を見抜けるか。B4より難易度高。

#### B6: 投稿更新のIDOR（所有者照合なし）
- **ファイル**: `server/src/routes/posts.routes.ts` (`updatePost`)
- **カテゴリ**: セキュリティ / 認可
- **難易度**: 中（○）
- **問題の形**: 投稿の `authorId` と `req.user.id` を照合せず、任意の投稿を更新可能。
- **本来あるべき修正**: `if (post.authorId !== req.user.id) return res.status(403)...` の所有者チェックを追加。
- **期待される検出挙動**: 認可チェックの欠如を指摘できるか。

#### B7: コメント削除のIDOR（所有者/管理者チェックなし）
- **ファイル**: `server/src/routes/comments.routes.ts` (`deleteComment`)
- **カテゴリ**: セキュリティ / 認可
- **難易度**: 中（○）
- **問題の形**: コメント投稿者・投稿の所有者・管理者のいずれのチェックもなく、任意のコメントを削除可能。
- **本来あるべき修正**: 投稿者本人または管理者のみ削除可、それ以外は403。
- **期待される検出挙動**: B6と同様、認可チェック欠如の指摘。

#### B8: 投稿作成の長大関数（単一責任原則違反）
- **ファイル**: `server/src/routes/posts.routes.ts` (`createPost`)
- **カテゴリ**: 可読性 / メンテナンス性
- **難易度**: 中（○）
- **問題の形**: バリデーション・画像アップロード・DB保存・メール通知・ログ出力を1つのハンドラに約120行で詰め込み、抽象化なし。
- **本来あるべき修正**: 関数を小さく分割し、ビジネスロジックをサービス層へ切り出し。
- **期待される検出挙動**: 長大関数・責務の混在として指摘できるか。

### PR-3: `feature/backend-ops`（並行性・TZ・リソース・情報漏洩）

#### C1: いいね競合（read-modify-write）
> ※ `likePost` は投稿機能ファイル（`posts.routes.ts`）に実装されるため、本問題は **PR-2 の差分**で評価されます。
- **ファイル**: `server/src/routes/posts.routes.ts` (`likePost`)
- **カテゴリ**: 並行性 / データ整合性
- **難易度**: 高（△）
- **問題の形**: `const post = await get(id); post.likes++; await save(post)` のように「読んで・書いて」でインクリメント。並列リクエストでいいね数が失われる。
- **本来あるべき修正**: `prisma.post.update({ data: { likes: { increment: 1 } } })` のアトミック更新、またはトランザクション内での行ロック。
- **期待される検出挙動**: レースコンディションを認識できるかが鍵。

#### C2: 会員登録の競合（UNIQUE制約欠如）
> ※ `register` メソッドは認証機能の一部として PR-1（`feature/backend-auth`）で実装されるため、本問題は **PR-1 の差分**で評価されます。
- **ファイル**: `server/src/services/users.service.ts` (`register`) / `server/prisma/schema.prisma`
- **カテゴリ**: 並行性 / データ整合性
- **難易度**: 高（△）
- **問題の形**: 先に `findByEmail` で重複チェックしてから `create` するが、DB側に `@@unique([email])` 制約がなく、並列リクエストで同一 email のアカウントが2件作られる（TOCTOU）。
- **本来あるべき修正**: `@@unique([email])` 制約を付与し、Prisma の `P2002` エラーを catch して「既に登録済み」を返す。
- **期待される検出挙動**: アプリ側チェックとDB制約の両面から指摘できるか。

#### C3: CSV出力のリソースリーク
- **ファイル**: `server/src/services/export.service.ts` (`exportPostsCsv`)
- **カテゴリ**: 堅牢性 / リソース管理
- **難易度**: 中（○）
- **問題の形**: `fs.createWriteStream` を開くが、エラー時の `finally` がなくストリームをクローズしない。一時ファイルの削除も漏れる。
- **本来あるべき修正**: `try/finally` または `using` 構文で確実にクローズ・削除。ストリームの `error`/`finish` を待機。
- **期待される検出挙動**: クリーンアップ欠如・ファイルディスクリプタリークとして指摘できるか。

#### C4: エラーレスポンスへのスタックトレース漏洩
- **ファイル**: `server/src/middleware/error.ts`
- **カテゴリ**: セキュリティ / 情報漏洩
- **難易度**: 低（◎）
- **問題の形**: `res.status(500).json({ error: err.message, stack: err.stack })` のように内部情報をクライアントに返す。
- **本来あるべき修正**: 本番では一般化メッセージ（"Internal Server Error"）を返し、`stack` はサーバログのみに出力。
- **期待される検出挙動**: 両ツールとも情報漏洩として指摘すべき。

#### C5: アクセスログへの機密情報混入
- **ファイル**: `server/src/middleware/logger.ts`
- **カテゴリ**: セキュリティ / 情報漏洩
- **難易度**: 中（○）
- **問題の形**: リクエストボディをそのままログ出力し、パスワード・メールアドレスがログに残る。
- **本来あるべき修正**: 機密フィールド（password 等）のマスキング、body は debug レベルのみ出力。
- **期待される検出挙動**: ログ経由の機密漏洩に言及できるか。

#### C6: デバッグエンドポイントの本番有効化
- **ファイル**: `server/src/routes/debug.routes.ts`
- **カテゴリ**: セキュリティ / 情報漏洩
- **難易度**: 中（○）
- **問題の形**: `/debug/state` がメモリ上のユーザ一覧やトークンをJSONで返し、本番環境でも有効。
- **本来あるべき修正**: 本番（`NODE_ENV === 'production'`）では無効化・ルータごと削除。
- **期待される検出挙動**: デバッグ機能の本番露出として指摘できるか。

#### C7: 公開スケジュールのタイムゾーン解釈
> ※ `schedulePost` は投稿機能ファイル（`posts.service.ts`）に実装されるため、本問題は **PR-2 の差分**で評価されます。
- **ファイル**: `server/src/services/posts.service.ts` (`schedulePost`)
- **カテゴリ**: 堅牢性 / 日時処理
- **難易度**: 高（△）
- **問題の形**: `new Date(publishAt)` でサーバローカルタイムゾーンとして解釈し、「9:00公開」の意図がUTC扱いでずれる。デプロイ先TZで結果が変わる。
- **本来あるべき修正**: ISO 8601（UTC、末尾 `Z`）で受渡しし、dayjs/date-fns-tz 等で明示的に正規化。サーバのローカルTZに依存しない。
- **期待される検出挙動**: TZ非依存の設計が必要な点に気付けるかが鍵。

### PR-4: `feature/frontend`（XSS・秘密・型・重複）

#### D1: Markdown描画のXSS（`dangerouslySetInnerHTML`）
- **ファイル**: `client/src/components/MarkdownRenderer.tsx`
- **カテゴリ**: セキュリティ / XSS
- **難易度**: 低（◎）
- **問題の形**: ユーザ入力のコメントを `marked()` でHTML化し、`dangerouslySetInnerHTML={{ __html: html }}` で直接描画。`<script>` や `onerror` 等の注入が実行される。
- **本来あるべき修正**: DOMPurify でサニタイズしてから描画、または `react-markdown` 等の安全なライブラリを使用。
- **期待される検出挙動**: 両ツールともXSSとして指摘すべき。

#### D2: 秘密のフロント埋め込み（APIキー・トークン）
- **ファイル**: `client/src/api/client.ts` / `client/src/pages/AdminPage.tsx`
- **カテゴリ**: セキュリティ / 機密管理
- **難易度**: 低（◎）
- **問題の形**: APIキーや一時トークンをソースコードにハードコード、または `localStorage` に保存。
- **本来あるべき修正**: 秘密はフロントに持たない。認証は httpOnly Cookie、APIキーはバックエンド経由で使用。
- **期待される検出挙動**: 両ツールともクライアント側の秘密管理として指摘すべき。

#### D3: 型安全性の欠如（`any` 多用・`@ts-ignore`）
- **ファイル**: `client/src/` 各コンポーネント（APIクライアント、コンテキスト等）
- **カテゴリ**: メンテナンス性 / 型安全性
- **難易度**: 低（◎）
- **問題の形**: レスポンスを `any` で受け、`@ts-ignore` で型エラーを握りつぶす。`shared/types.ts` との整合がない。
- **本来あるべき修正**: 正しい Generic と `shared/types.ts` の型を用い、`@ts-ignore` を排除。
- **期待される検出挙動**: 両ツールとも `any` 濫用・型放棄として指摘すべき。

#### D4: 日付フォーマットロジックの重複（client / server）
